# 게임 상세 기획서 작성 원칙 (교재 요약)

이 문서는 `reference/textbook.pdf`(프로그래머가 AI 시대에 쓰는 게임 상세 기획서 작성법, Part 1~13 / Chapter 1~120)의 요약이며, 이 리포지토리에서 기획 문서를 작성할 때 따르는 작성 원칙이다.

---

## Part별 목적 요약

### Part 1. AI 시대, 왜 프로그래머에게 기획서가 필요한가
바이브 코딩으로 개발 속도가 빨라질수록 "무엇을 만들지" 정확히 설명하는 능력이 더 중요해진다는 점을 설명한다.
기획자가 없는 프로젝트에서 생기는 문제(방향 흔들림, 기능 충돌, AI 결과 불안정)를 짚는다.
이 책이 목표로 하는 상세 기획서의 최종 형태(개요, 루프, 시스템, UI, 레벨, 데이터, 예외, AI 프롬프트)를 제시한다.

### Part 2. 게임 아이디어를 개발 가능한 문장으로 바꾸기
"재미있는 액션 게임" 같은 막연한 아이디어를 구현 가능한 기획으로 바꾸는 과정을 다룬다.
콘셉트 한 문장, 타깃 유저, 장르, 참고 게임 분석, 핵심 재미 분해를 통해 필요한 시스템을 끌어낸다.
만들고 싶은 것과 만들 수 있는 것을 구분하고 MVP 기준으로 범위를 줄인다.

### Part 3. 게임 상세 기획서의 기본 구조
상세 기획서에 반드시 들어가야 할 항목의 뼈대를 잡는다.
게임 개요, 핵심 플레이 루프, 주요 시스템 목록, 화면 목록, 데이터 목록, 기능 우선순위, 예외 조건을 순서대로 설명한다.
개요 문서와 상세 기획서의 역할 차이를 구분해 문서가 개발 기준으로 쓰이게 만든다.

### Part 4. 플레이어 조작과 캐릭터 기획하기
플레이어 입력과 캐릭터 동작을 구현 가능한 명세로 정리하는 방법을 다룬다.
입력 명세, 이동/점프/대시 정의, 가능·불가능 조건, 상태 머신(Idle, Move, Attack, Hit, Dead), 애니메이션 전환 조건, 능력치 정의를 순서대로 작성한다.
마지막에 캐릭터 기획서를 클래스와 데이터 구조로 연결한다.

### Part 5. 전투 시스템 상세 기획하기
전투를 하나의 기능이 아니라 규칙의 집합으로 보고 분해하는 방법을 다룬다.
공격 입력과 판정, 데미지 계산식, 체력·방어력·치명타 수치, 피격·넉백·무적 시간, 스킬과 쿨타임, 적 AI, 보스 페이즈를 각각 조건으로 정의한다.
정리한 전투 기획서를 AI 구현 요청 프롬프트로 변환하는 과정까지 다룬다.

### Part 6. 성장, 아이템, 보상 시스템 기획하기
반복 플레이를 이끄는 성장·아이템·보상 구조를 데이터와 규칙 중심으로 정리한다.
경험치와 레벨업 규칙, 능력치 상승 구조, 아이템 종류와 속성, 보상 테이블, 드랍 확률, 재화, 상점을 다룬다.
어떤 값을 테이블로 분리하고 어떤 조건을 예외 처리할지 판단 기준을 제시한다.

### Part 7. UI와 화면 흐름 상세 기획하기
UI를 꾸미기 전에 화면 목록부터 정리하는 방법을 다룬다.
타이틀, 로비, 인게임 HUD, 인벤토리, 상점, 설정 화면의 표시 데이터·버튼 동작·갱신 조건을 정의하고 팝업/토스트/확인창 규칙과 화면 전환 흐름도를 작성한다.
마지막에 UI 기획서를 구현 요청 프롬프트로 변환한다.

### Part 8. 레벨과 스테이지 기획하기
스테이지를 배경이 아니라 목표·도전·보상의 구조로 설계하는 방법을 다룬다.
스테이지 목표, 진행 흐름, 오브젝트 배치 기준, 적 배치와 난이도 곡선, 튜토리얼, 반복 플레이 구간, 체크포인트와 실패 조건을 정리한다.
레벨 기획을 표로 정리해 그대로 데이터 설계로 이어지게 한다.

### Part 9. 데이터 중심으로 상세 기획서 작성하기
게임 규칙 대부분이 결국 데이터로 표현된다는 관점에서 데이터 기획을 다룬다.
하드코딩할 값과 데이터화할 값을 구분하고, 캐릭터·아이템·스킬·스테이지·퀘스트 데이터를 테이블로 구성한다.
밸런싱 수치를 표로 관리하고 이를 ScriptableObject 같은 실제 구조로 연결한다.

### Part 10. 시스템 흐름과 예외 조건 작성하기
정상 흐름만이 아니라 실패와 예외 상황까지 정의하는 방법을 다룬다.
게임 시작·종료 흐름, 승리·패배 조건, 저장과 불러오기, 네트워크 끊김, 보상 중복 지급, 비정상 입력과 악용 가능성을 정리한다.
상태 전환표와 플로우차트로 흐름을 시각화해 구현 중 즉흥적 판단을 줄인다.

### Part 11. 상세 기획서를 AI 프롬프트로 바꾸기
작성한 기획서를 AI 개발 요청 프롬프트로 변환하는 방법을 다룬다.
기능 구현 요청, 클래스 설계 요청, UI 구현 요청, 테스트 코드 요청으로 각각 변환하는 순서를 제시한다.
AI 결과를 검토하는 기준, 잘못된 결과를 다시 요청하는 방법, 프롬프트 수정 이력 관리도 함께 다룬다.

### Part 12. 미니 프로젝트로 상세 기획서 작성하기
작은 스테이지형 액션 RPG를 예시로 상세 기획서 한 벌을 처음부터 끝까지 작성한다.
콘셉트, 핵심 플레이 루프, 조작, 전투, 아이템과 보상, UI, 스테이지, 데이터 테이블을 순서대로 만든다.
이를 AI 구현 요청 프롬프트로 바꾸고, 결과를 검토해 기획서를 수정하고 최종 문서로 통합한다.

### Part 13. 프로그래머의 기획 습관 만들기
기획서를 일회성 문서가 아니라 계속 갱신되는 개발 기준으로 유지하는 습관을 다룬다.
구현하면서 기획서를 업데이트하고, 코드 변경과 문서 변경을 함께 관리하며, Git과 README로 문서와 코드를 연결한다.
작은 게임을 반복해 기획하며 기획 감각을 키우고, AI 시대에도 명확한 생각이 출발점임을 강조한다.

## 작성 원칙 (규칙 목록)

### 방향과 범위 정하기

- 게임을 한 문장 콘셉트로 먼저 정의한다. 감상적 표현 대신 장르·플레이 목표·주요 행동이 드러나게 쓴다. (Ch.10, Ch.19)
- 타깃 유저를 정의하고, 그 유저에게 필요한 기능인지로 기능 추가를 판단한다. (Ch.11)
- 중심 장르와 대상 플랫폼을 먼저 정하고, 그 장르에 필요한 핵심 시스템을 목록으로 뽑는다. (Ch.12, Ch.19, Ch.26)
- 참고 게임은 "재미있다"로 끝내지 말고 기능·규칙·데이터·흐름으로 분해해 내 언어로 다시 정리한다. (Ch.13)
- 핵심 재미는 감각적인 한 단어로 두지 말고 여러 기능 단위로 분해해 적는다. ("타격감" → 공격 판정, 피격 경직, 넉백, 이펙트 타이밍) (Ch.14)
- 기능은 필수·중요·선택으로 나누고, 이번 버전(MVP)에 포함할 범위와 제외할 범위를 명시한다. 기능마다 하위 작업을 적어 실제 작업량을 드러낸다. (Ch.15, Ch.16, Ch.19, Ch.24)
- 개요 문서와 상세 기획서를 구분한다. 개요는 방향을, 상세 기획서는 입력·처리·결과·예외를 담는다. (Ch.18)
- 핵심 플레이 루프를 4~6단계로 짧게 쓰고, 루프의 각 단계에서 필요한 시스템 목록을 뽑는다. (Ch.20, Ch.21, Ch.101)
- 문서는 게임 개요 → 핵심 플레이 루프 → 시스템 → 화면 → 데이터 → 예외 조건 → AI 구현 요청 프롬프트 순서로 구성한다. (Ch.8, Ch.17, Ch.110)

### 문장 쓰는 법

- 하나의 기능은 목적, 조건(입력), 처리 흐름, 결과, 예외로 분해해서 쓴다. (Ch.8, Ch.17, Ch.90)
- 모호한 표현을 쓰지 않는다. "재미있는", "적당히", "자연스럽게", "알아서", "좋은 느낌으로"는 구체적인 조건과 수치로 바꾼다. (Ch.9, Ch.10, Ch.90)
- 정상 흐름만 쓰지 말고, 실패·부족·중복·잘못된 입력 같은 예외 조건과 제한 사항을 반드시 함께 쓴다. (Ch.7, Ch.25, Ch.81)
- 협업 문서는 문서의 목적과 적용 범위를 먼저 밝히고, 기능 개요·UI 요소·데이터 항목·처리 흐름·예외 조건·테스트 기준을 구분해 쓴다. (Ch.116)

### 조작·전투·시스템

- 입력은 "무엇을 누르면 무엇이 된다"만 쓰지 말고, 가능한 조건과 불가능한 조건, 입력 시점(누르는 순간·누르는 동안·떼는 순간)을 함께 쓴다. (Ch.26, Ch.27, Ch.28, Ch.102)
- 상태가 있는 기능은 상태 목록, 진입 조건, 유지 중 가능한 행동, 종료 조건을 상태 전환표로 정리한다. (Ch.29, Ch.30, Ch.88)
- 애니메이션은 상태와 연결해 전환 조건을 쓰고, 겹칠 때의 우선순위와 취소 여부까지 정한다. (Ch.31)
- 판정과 효과가 발생하는 시점을 초·프레임 단위로 적는다. ("공격 애니메이션 시작 후 0.2초에 판정 발생") (Ch.35)
- 계산식은 결과값만 적지 말고 계산 순서, 최소·최대값, 보정 적용 순서를 함께 적는다. (Ch.36, Ch.37, Ch.45, Ch.52)
- 피격은 체력 감소만 쓰지 말고 상태 전환, 넉백 방향·거리·시간, 무적 시간까지 적는다. (Ch.38)
- 스킬은 이름과 느낌 대신 입력 조건, 효과, 대상, 범위, 자원 소모, 쿨타임, 사용 불가 조건으로 정의한다. (Ch.39)
- 적과 보스는 상태별 감지·공격 조건, 예고 동작, 패턴 쿨타임, 페이즈 전환 기준을 적어 예측 가능하게 만든다. (Ch.40, Ch.41)
- 화면은 목록 → 표시 데이터 → 버튼 동작 → 갱신 조건 → 전환 흐름 순으로 정리한다. (Ch.22, Ch.53, Ch.61, Ch.105)
- 팝업·토스트·확인창은 역할을 구분해 표시 시간, 중첩 허용 여부, 뒤쪽 입력 차단 규칙을 정한다. (Ch.60)
- 스테이지는 목표, 구간별 진행 흐름, 오브젝트·적 배치와 난이도 곡선, 체크포인트 복구 범위를 함께 적는다. (Ch.64, Ch.65, Ch.66, Ch.67, Ch.70)
- 튜토리얼은 한 번에 하나씩 가르치도록 구간을 나누고, 각 구간의 안내 표시 조건과 완료 조건을 적는다. (Ch.68)
- 스테이지 정보는 문장만이 아니라 ID·목표 타입·적 그룹·보상 테이블·난이도·다음 스테이지가 있는 비교 가능한 표로도 정리한다. (Ch.71, Ch.77)
- 승리·패배, 클리어·실패 조건은 판단 가능한 조건으로 쓰고, 동시에 성립할 때의 우선순위도 정한다. (Ch.70, Ch.83)

### 데이터

- 수치는 문장에 흩어놓지 말고 표(데이터 테이블)로 정리해 비교 가능하게 만든다. (Ch.23, Ch.71, Ch.79)
- 자주 바뀌는 밸런싱 값은 데이터로 빼고, 거의 바뀌지 않는 내부 규칙만 코드에 둔다. (변경 주체와 변경 빈도로 판단) (Ch.72, Ch.73)
- 고정 기준 데이터와 플레이어별 진행·상태 데이터를 분리해서 정의한다. (Ch.78, Ch.80)
- 데이터 항목에는 필드 이름과 함께 타입, 단위, 값 범위를 적는다. (확률이 0~1인지 0~100인지 명시) (Ch.79, Ch.107)
- 내부 참조용 ID와 화면 표시용 이름을 분리하고, ID 중복을 막는 명명 규칙을 미리 정한다. (Ch.74, Ch.75, Ch.76, Ch.77)
- 필드 이름은 코드에서 쓸 이름과 일치시키고 문서 전체에서 일관되게 쓴다. (Hp/Health/MaxHealth 혼용 금지) (Ch.74, Ch.79, Ch.80)
- 밸런싱 표는 기준 단위(레벨 기준인지 스테이지 기준인지)를 먼저 정하고 섞지 않는다. (Ch.79)
- 보상은 지급 조건, 확률 방식(독립 확률인지 가중치 선택인지), 지급 수량 범위까지 적고, 반복 구간은 고정 보상·확률 보상·최초 클리어 보상·지급 제한을 구분한다. (Ch.48, Ch.49, Ch.69)

### 예외와 흐름

- 저장할 데이터, 저장 시점, 저장 데이터가 없거나 손상됐을 때의 처리를 명시한다. (Ch.82, Ch.84)
- 네트워크가 필요한 기능은 끊김 시 화면 처리와 재시도 규칙, 재화·아이템 데이터의 무결성 규칙을 적는다. (Ch.85)
- 보상은 1회 지급인지 반복 지급인지 구분하고, 지급 상태를 저장해 중복 지급을 막는 조건을 적는다. (Ch.86)
- 연타, 중복 클릭, 로딩 중 입력, 사망 상태 입력 같은 비정상 입력과 악용 가능성을 기능별로 미리 정리한다. (Ch.87)
- 조건 분기가 많은 흐름은 플로우차트로 시작·종료 지점과 분기를 정리한 뒤 문장으로 풀어 쓴다. (Ch.89)

### AI에게 요청하기

- 기획서를 AI 프롬프트로 바꿀 때는 "환경 → 목적 → 기존 구조 → 구현 기능 → 데이터 구조 → 처리 흐름 → 예외 조건 → 출력 형식" 순으로 쓴다. (Ch.42, Ch.91, Ch.108)
- 기능은 한 번에 전부 요청하지 말고 동작 단위로 나누어, 정해진 순서대로 요청한다. (Ch.91, Ch.108, Ch.110)
- 클래스 설계를 요청할 때는 데이터·로직·UI의 책임을 분리하도록 명시한다. (Ch.33, Ch.93)
- 기획서의 조건을 그대로 테스트 케이스(입력값과 기대 결과)로 바꿔 검증 기준을 만든다. (Ch.95)
- AI 결과는 기획서 요구사항 충족, 기존 프로젝트 구조와의 일관성, 데이터 변경의 안전성 세 기준으로 검토한다. (Ch.96, Ch.109)
- 잘못된 결과는 "문제 상황 → 의심되는 원인 → 기대 동작 → 변경 제한" 순으로 좁혀서 다시 요청한다. (Ch.97)
- 프롬프트 수정 이력(요청 목적, 사용한 프롬프트, 발견한 문제, 수정 사유, 최종 결과)을 짧게 남긴다. (Ch.98)

### 문서 유지 관리

- 기획서를 한 번에 완성하려 하지 말고, 필요한 만큼 쓰고 구현하며 단계적으로 보완한다. (Ch.111)
- 구현 중 결정한 조건·제한 사항·데이터 변경은 코드에만 넣지 말고 날짜와 함께 기획서에 짧게 기록한다. (Ch.112)
- 기획 감각을 위해 작은 게임을 여러 개 1~2페이지 분량으로 기획해보고, 부족한 문장이 무엇인지 프롬프트로 바꿔 확인한다. (Ch.118, Ch.119)
- 코드를 고치면 해당 기능의 기획서와 데이터 테이블도 같이 고쳐 기준을 하나로 유지한다. (Ch.113)
- 기획서는 .md로 작성해 기능별로 나누고 Git으로 버전 관리하며, 커밋 메시지에 변경 이유를 남긴다. (Ch.114)
- README에 게임 개요와 기획 문서 목록, 대응하는 코드 폴더를 연결해 진입점으로 쓴다. (Ch.115)
- 혼자 개발하더라도 콘셉트, 핵심 루프, 기능 목록, 데이터 테이블, 예외 조건, 구현 요청 프롬프트는 문서로 남긴다. (Ch.117)
- 최종 점검에서 문서 간 연결이 끊기지 않았는지 확인한다. (조작↔전투 판정, 아이템↔UI 표시, 스테이지 보상↔보상 테이블 수치) (Ch.110)
